# 논술형 평가 자동채점 웹앱 — 아키텍처 설계

작성일: 2026-08-15
상태: 초안 (검토 대기)
구현 예정: Codex

---

## 1. 목표

교사가 논술형 평가의 **채점기준과 예시답안을 업로드**하고, 학생들이 손으로 작성한 답안지를 **한 번에 스캔한 PDF 1개**를 업로드하면, 학생별로 자동 채점하고 개별 피드백을 생성하는 웹앱.

특정 교과·특정 시험에 종속되지 않는 **범용 플랫폼**이다. 첨부된 「2026 경기도교육청 초등 기본학력 평가 - 수학 논술형」은 설계 검증용 예시일 뿐이다.

### 채점 확정 모델

이원화 방식을 채택한다.

- **자동 확정**: 정답이 고정된 문항(단답·기호·수치·택일) 중 인식 신뢰도가 임계값 이상인 것
- **교사 검토**: 작도 문항, 서술 문항, 그리고 신뢰도가 임계값 미만인 모든 항목

앱은 모든 문항에 점수를 **제안**하고 근거를 제시한다. 자동 확정 대상은 교사가 넘기면 그대로 확정되고, 검토 대상은 교사가 확인·수정해야 확정된다.

## 2. 핵심 설계 원칙

### 원칙 1 — LLM은 채점자가 아니라 컴파일러다

LLM이 개입하는 지점을 두 곳으로만 제한한다.

1. **루브릭 컴파일 (평가당 1회)**: 채점기준표·예시답안 PDF를 읽어 구조화된 루브릭 JSON으로 변환한다. 교사가 검토·수정 후 확정한다.
2. **서술형 판정 (답안당)**: 자유 서술 문항만 판정한다.

나머지 채점은 전부 결정론적 코드다.

**근거**: 학생 답안마다 LLM이 전체 채점을 수행하면, LLM 오류가 학생 수만큼 반복되고 아무도 발견하지 못한다. 루브릭 컴파일은 오류가 **1회 발생하고 교사가 확정 화면에서 잡는다.** 오류가 증폭되지 않는다.

### 원칙 2 — 폐집합(closed set)으로 인식 오류를 흡수한다

정답 후보를 미리 알 수 있는 문항은, 인식 결과를 자유롭게 받지 않고 **후보 집합으로 스냅**한다. 손글씨가 `l0,000`으로 읽혀도 후보 `{10,000, 6,000, 4,000}` 중 최근접으로 복원되어 정확히 채점된다.

루브릭 컴파일러의 가장 중요한 산출물이 이 **정답 후보 집합**이다.

### 원칙 3 — 모든 점수에 추적 가능한 근거를 붙인다

점수 하나마다 다음을 저장한다.

- 답안 이미지의 해당 영역 좌표 (교사 UI에서 크롭 표시)
- 인식된 텍스트/도형 원본
- 적용된 루브릭 조항 원문
- 신뢰도 값

이의제기 대응과 교사 검토 속도 모두 여기에 달려 있다.

### 원칙 4 — 인식·판정 계층은 교체 가능한 어댑터다

OCR 엔진과 LLM 제공자를 인터페이스 뒤에 둔다. 제공자 교체와 온프레미스 전환이 가능해야 한다.

### 원칙 5 — 식별정보는 경계를 넘지 않는다

**클라우드 API를 사용하되, 학생을 식별할 수 있는 정보는 로컬 경계 안에 머문다.**

이름·학교·반·번호는 답안지에서 물리적으로 분리하여 로컬에서만 처리하고, 외부로는 **익명 토큰이 붙은 답안 본문 영역만** 전송한다. 상세 설계는 §7.7 참조.

이 원칙은 코드 구조로 강제한다. 외부 전송을 수행하는 모든 경로는 **단일 게이트웨이 모듈**을 통과해야 하며, 게이트웨이는 전송 직전 PII 검사를 수행하고 실패 시 예외를 던진다. 어댑터가 직접 네트워크를 호출하는 구조를 금지한다.

## 3. 범위

### v1 포함

- 평가 저작 (평가명, 교과, 학년, 성취기준, 성취수준)
- 채점기준표·예시답안 PDF 업로드 및 루브릭 자동 컴파일
- 빈 답안지 PDF 업로드 및 문항 응답 영역 지정
- 명렬표 업로드
- 대량 스캔 PDF 업로드 → 쪽수 기반 학생 분할 + 검증
- 페이지 정합 및 학생 필기 추출
- 문항 유형별 채점 (폐집합/수치/택일/서술)
- 신뢰도 기반 자동확정·검토 라우팅
- 교사 검토·확정 UI
- 학생별 피드백 자동 생성
- 결과 내보내기 (Excel, 학생별 피드백 PDF)

### v1 제외 (v2 이후)

- **작도 문항 자동 채점** — v1에서는 무조건 교사 검토로 라우팅한다. 예시답안과 학생 답안을 나란히 띄우고 배점 버튼만 제공한다.
- 격자형 작도 전용 기하 판정 플러그인
- 학생·학부모 열람 포털
- NEIS 연계
- 문항 분석 통계 (변별도, 난이도)

**작도 자동채점을 제외하는 이유**: 격자 기반 대칭 판정은 답안지가 격자를 제공하는 경우에만 성립한다. 범용 엔진에 일반화할 수 없으며, 잘못 일반화하면 신뢰도가 무너진다. 예시 시험 기준으로 20점 중 6점(30%)이 교사 검토로 간다.

## 4. 사용자 흐름

```
[준비 단계 — 평가당 1회]
1. 평가 생성        평가명, 교과, 학년, 학급
2. 성취기준 입력     공통핵심기준 + 성취수준(1/2/3수준) 서술
3. 문서 업로드       채점기준표 PDF, 예시답안 PDF, 빈 답안지 PDF
4. 루브릭 컴파일     LLM이 문항 구조 추출 → 교사 검토·수정 → 확정
5. 응답 영역 지정     빈 답안지 위에서 문항별 영역 드래그 → 교사 확인
6. 명렬표 업로드     번호, 이름 (결시자 체크)

[채점 단계 — 배치당 1회]
7. 스캔 PDF 업로드   전체 학생 답안 1개 파일
8. 분할 및 검증      쪽수 기반 분할 → 이름란 대조 → 불일치 시 중단
9. 인식 및 채점      3계층 채점 엔진 실행
10. 교사 검토        검토 큐 처리 → 확정
11. 피드백 생성      확정된 점수 기준으로 생성
12. 내보내기         성적표, 개별 피드백
```

**중요**: 피드백은 **교사가 점수를 확정한 후에만** 생성한다. 미확정 점수로 피드백을 만들면 교사가 점수를 고쳤을 때 피드백과 어긋난다.

### 컴포넌트 책임

| 컴포넌트 | 책임 | 의존 |
|---|---|---|
| 루브릭 컴파일러 | 채점기준 PDF → 루브릭 JSON | LLMProvider |

## 6. 루브릭 스키마

시스템의 중심 자료구조다. 루브릭 컴파일러의 출력이자 채점 엔진의 입력이다.

```jsonc
{
  "assessment": {
    "title": "2026 경기도교육청 초등 기본학력 평가 - 수학 논술형",
    "subject": "수학",
    "grade": 6,
    "total_points": 20
  },
  "achievement_standards": [
    {
      "id": "AS1",
      "item_range": [1, 4],
      "core_standard": "선대칭 도형과 점대칭 도형의 의미와 대칭인 도형 간의 성질을 이해하고, 대칭인 도형을 그린다.",
      "levels": {
        "1": "선대칭 도형과 점대칭 도형의 의미와 성질을 알고, 조건에 맞게 간단한 대칭인 도형을 그리려고 시도한다.",
        "2": "…",
        "3": "…"
      }
    }
  ],
  "items": [
    {
      "item_no": 1,
      "title": "대칭축과 대칭의 중심 찾아보기",
      "points": 2,
      "standard_id": "AS1",
      "type": "closed_short",          // 아래 유형 목록 참조
      "blanks": [
        { "key": "①", "answers": ["선대칭"], "aliases": ["선 대칭", "선대칭 도형"] },
        { "key": "②", "answers": ["점대칭"], "aliases": ["점 대칭", "점대칭 도형"] }
      ],
      "scoring": [
        { "score": 2, "condition": "all_correct",  "criterion": "선대칭과 점대칭 도형을 정확하게 씀" },
        { "score": 1, "condition": "partial:1",    "criterion": "선대칭, 점대칭 도형 중 한 가지만 옳게 씀" },
        { "score": 0, "condition": "none_correct", "criterion": "선대칭, 점대칭 도형을 쓰지 못하거나 내용이 모두 옳지 않음" }
      ]
    }
  ],
  "level_cutoffs": { "3": 17, "2": 11, "1": 0 }
}
```

### 문항 유형

| 유형 | 설명 | 채점기 | 예시 문항 |
|---|---|---|---|
| `closed_short` | 정답 후보가 유한한 단답 | 결정론 (폐집합 스냅) | 1, 5 |
| `closed_table` | 표 셀에 기호 배치 | 결정론 (집합 비교) | 2 |
| `numeric` | 수치 정답 | 결정론 (정규화 후 비교) | 7 일부, 8 일부 |
| `choice` | 택일 (동그라미/체크) | 결정론 (마크 검출) | 8 판단 |
| `drawing` | 작도 | **v1: 교사 검토 강제** | 3, 4 |
| `open_text` | 자유 서술 | LLM 판정 | 6, 7 과정, 8 이유 |
| `composite` | 위 유형이 한 문항에 혼재 | 하위 파트별 분해 후 합산 | 6, 7, 8 |

`composite`가 실무에서 가장 흔하다. 7번은 `open_text`(계산 과정) + `numeric`(25, 30) + `closed_short`(샤프)의 합성이다. 컴파일러는 이를 하위 파트로 분해해야 한다.

### `scoring.condition` 문법

결정론 채점기가 해석하는 조건식이다.

- `all_correct` — 모든 blank/파트 정답
- `partial:N` — 정확히 N개 정답
- `partial:>=N` — N개 이상 정답
- `none_correct` — 전부 오답
- `set_exact` — 집합이 정확히 일치 (`closed_table`)
- `set_partial` — 일부만 일치
- `llm` — LLM 판정에 위임 (`open_text`)
- `manual` — 교사 판정 필수 (`drawing`)

## 7. 파이프라인 상세

### 7.1 스캔 PDF 분할

**입력**: 전체 학생 답안 스캔 PDF 1개, 빈 답안지 PDF, 명렬표

```
1. 학생 1인당 쪽수 N = 빈 답안지 PDF의 쪽수
2. 전체 쪽수 P 확인
3. 백지 페이지 감지 (양면 스캔 시 빈 뒷면 제거 옵션)
4. 기대 학생 수 = 명렬표 인원 − 결시자
5. 검증: P == N × 기대 학생 수 ?
      아니면 → 배치 중단, 교사에게 원인 표시
6. N쪽씩 순차 분할 → 명렬표 번호 순으로 배정
7. 배정 검증 (아래)
```

**배정 검증 — 1차: 페이지 마커 (결정론)**

답안지 양식을 수정할 수 있으므로, 각 쪽 하단에 **쪽 번호 마커**(1..N을 나타내는 QR 또는 바코드)를 인쇄한다. 모든 학생의 답안지는 동일하므로 개인정보가 담기지 않는다.

스캔본에서 마커를 읽으면 기대 수열은 `1,2,…,N,1,2,…,N,…` 이다. 이 수열이 깨지는 지점이 곧 급지 사고 지점이다.

```
읽은 수열: 1,2,3, 1,2,3, 1,3, 1,2,3, …
                        ↑ 8번째 페이지에서 2가 누락 — 3번 학생 구간
```

**이 검사는 손글씨 인식에 의존하지 않으므로 거의 확실하게 동작한다.** 이름란 OCR보다 훨씬 강력한 1차 방어선이며, 답안지 수정이 가능해진 덕분에 확보된 이점이다.

**배정 검증 — 2차: 이름란 대조**

페이지 마커를 통과한 뒤, 각 학생 묶음의 첫 페이지에서 이름·번호란 영역을 로컬 OCR한다. 이 값을 명렬표와 **폐집합 매칭**한다. 마커가 정상이어도 답안지 배부 순서가 뒤바뀐 경우를 잡는다.

- 전원 일치 → 진행
- 하나라도 불일치 → **배치 전체 중단**, 불일치 지점을 교사에게 표시하고 수동 재배정 UI 제공

이 검증이 없으면 급지 불량 한 번으로 전원이 오채점되고, 채점은 정상적으로 완료된 것처럼 보인다. 검증을 선택 기능으로 두어서는 안 된다.

**이름란 OCR이 실패해도** 그것만으로 중단하지 않는다. 판정 규칙:

| 이름란 인식 | 명렬표 대조 | 처리 |
|---|---|---|
| 성공 | 일치 | 진행 |
| 성공 | 불일치 | **배치 중단** |
| 실패/공란 | — | 해당 학생만 "배정 확인" 플래그, 나머지 진행 |

### 7.2 페이지 정합 (registration)

각 스캔 페이지를 빈 답안지 템플릿에 맞춘다.

```
1. 템플릿과 스캔본에서 특징점 추출 (ORB)
2. 매칭 → RANSAC → homography 산출
3. 스캔본을 템플릿 좌표계로 워핑
4. 정합 품질 점수 산출 (inlier 비율)
   임계값 미만 → 해당 페이지 "정합 실패" 플래그 → 교사 검토
```

답안지에 표와 괘선이 많아 특징점이 충분하다. 기준 마커가 없어도 동작하지만, **향후 답안지를 제작할 수 있다면 네 모서리에 마커를 넣는 것을 권장**한다.

### 7.3 학생 필기 추출

정합된 스캔본에서 템플릿을 차분하여 인쇄 요소를 제거한다.

```
1. 두 이미지를 그레이스케일 정규화 (조명 보정)
2. 차분 → 학생 필기 마스크
3. 형태학적 연산으로 노이즈 제거
4. 잔여 인쇄선 제거 (정합 오차 보정)
```

이 결과가 작도 문항 처리와 영역별 인식의 입력이 된다.

### 7.4 인식

문항별 응답 영역을 크롭하여 유형에 맞는 인식기에 넘긴다.

| 문항 유형 | 인식 경로 |
|---|---|
| `closed_short`, `closed_table`, `numeric`, `choice` | **후보 제시 분류 질의** (아래) |
| `open_text` | 전사(transcription) 질의 → 텍스트 → 실명 마스킹 |
| `drawing` | 인식하지 않음. 필기 마스크만 보존하고 교사 검토로 직행 |

**후보 제시 분류 질의 — 전사를 건너뛴다**

폐집합 문항에서는 "학생이 쓴 글자를 정확히 옮겨 적는" 전사 문제를 풀 필요가 없다. 정답 후보를 이미 알고 있으므로, 멀티모달 모델에 **후보 목록과 함께 이미지를 주고 어느 것인지 고르게** 한다.

```
"이 손글씨가 다음 중 무엇입니까?
 ① 10,000  ② 6,000  ③ 4,000  ④ 위 어느 것도 아님  ⑤ 판독 불가"
```

전사 정확도의 병목을 우회하고, 오인식이 후보 밖으로 나갈 수 없다. `④`와 `⑤`를 반드시 선택지에 넣어야 모델이 억지로 하나를 고르지 않는다. 원문자 손글씨(`㉠~㉦`)처럼 전사가 어려운 대상에서 특히 유리하다.

전사 경로(`open_text`)에는 폐집합이 없으므로 이 기법을 쓸 수 없다. 그래서 서술 문항이 P3에서 가장 불확실한 구간으로 남는다.

**폐집합 스냅 알고리즘**

```
후보 = 정답 후보 ∪ 오답 후보(루브릭에 명시된 것)
정규화(공백, 전각/반각, 쉼표, 단위 제거)
각 후보와 편집거리 계산
최소 거리 후보 선택
거리 > 임계값이면 "인식 불가" → 교사 검토
```

**수치 정규화 규칙** (오인식이 가장 치명적인 지점)

- 쉼표 제거: `10,000` → `10000`
- 단위 제거: `10,000원` → `10000`
- 백분율: `25%`, `25 %`, `25퍼센트` → `25`
- **쉼표와 소수점 혼동 방지**: 천단위 구분 위치(뒤에서 3자리)면 쉼표로 간주

### 7.5 채점

```python
def grade_item(item: RubricItem, response: RecognizedResponse) -> ItemScore:
    if item.type == "drawing":
        return ItemScore(score=None, route="manual", reason="작도 문항")
    if item.type == "open_text":
        return llm_grader.grade(item, response)
    if item.type == "composite":
        parts = [grade_part(p, response) for p in item.parts]
        return combine(item, parts)
    return deterministic_grader.grade(item, response)
```

**LLM 채점기 출력 계약**

```jsonc
{
  "score": 2,
  "matched_criterion": "두 물건의 할인율을 백분율로 정확하게 나타냈으나 풀이 과정에 일부 오류가 있음",
  "evidence": "학생 답안에서 인용한 실제 문구",
  "reasoning": "왜 이 점수인지",
  "confidence": 0.78
}
```

`score`는 반드시 루브릭에 존재하는 배점 값 중 하나여야 한다. 아니면 거부하고 교사 검토로 보낸다. `matched_criterion`도 루브릭 원문과 일치해야 한다. **LLM이 새로운 점수나 새로운 기준을 발명하지 못하게 막는 것**이 핵심이다.

### 7.6 신뢰도 및 라우팅

```
자동 확정 조건 (모두 만족):
  - 문항 유형이 closed_short / closed_table / numeric / choice
  - 인식 신뢰도 ≥ 0.90
  - 폐집합 스냅 거리가 임계값 이내
  - 페이지 정합 성공
  - 배정 검증 통과

그 외 전부 → 교사 검토 큐
```

임계값은 설정 가능해야 한다. 운영 초기에는 **모든 항목을 검토로 보내는 모드**를 제공하여, 실측 정확도가 쌓인 후 자동 확정 범위를 넓히는 것을 권장한다.

### 7.7 비식별화 및 외부 전송 경계

**정책: 비식별화 후 클라우드 사용.** 인식·판정에는 클라우드 API를 쓰되, 학생 식별정보는 외부로 나가지 않는다.

#### 경계 구분

```
┌─── 로컬 경계 (교내/서버 내부) ────────────────────┐
│                                                  │
│  원본 스캔 PDF                                    │
│  PII 영역 크롭 (이름·학교·반·번호)                 │
│  로컬 OCR → 명렬표 폐집합 매칭 → 배정 검증          │
│  학생 ↔ 익명 토큰 매핑표                           │
│  확정 점수 · 피드백 최종본 (실명 삽입)              │
│                                                  │
│         ┌──────────────────────────┐             │
│         │  전송 게이트웨이           │             │
│         │  · PII 영역 마스킹 검증    │             │
│         │  · 실명 문자열 스캔        │             │
│         │  · 익명 토큰 치환          │             │
│         │  · 감사 로그 기록          │             │
│         └───────────┬──────────────┘             │
└─────────────────────┼────────────────────────────┘
                      ▼
        ┌─────────────────────────────┐
        │ 클라우드 (OCR / LLM API)     │
        │  답안 본문 영역 이미지        │
        │  익명 토큰 (예: S-7f3a)      │
        │  루브릭 (개인정보 없음)       │
        └─────────────────────────────┘
```

#### 구현 규칙

**1. PII 영역 지정 (템플릿 단계)**

`SheetTemplate`의 영역 지정 UI에서 응답 영역과 별도로 **PII 영역**을 지정한다. 이 영역은 `region_type = "pii"`로 표시되며, 전송 대상에서 원천 제외된다.

예시 답안지에서는 첫 페이지 상단의 `학교 / 학년 / 반 / 번 / 이름` 표가 여기 해당한다.

**2. PII 영역은 로컬에서만 처리**

- 이름란 OCR은 **로컬 경량 OCR 엔진**으로 수행한다
- 결과를 명렬표와 폐집합 매칭한다 (§7.1 배정 검증)
- **로컬 OCR 정확도가 클라우드보다 낮다는 점은 감수한다.** 다만 명렬표라는 폐집합이 있어 실질 정확도는 크게 떨어지지 않는다. 매칭 실패는 오채점이 아니라 "배정 확인" 플래그로 이어지므로 안전 방향으로 실패한다.

**3. 전송 전 마스킹**

답안 본문 크롭을 만들 때 PII 영역과 겹치는 픽셀은 단색으로 채운다. 크롭 좌표가 PII 영역과 교차하면 게이트웨이가 전송을 거부한다.

**4. 답안 본문 내 실명 노출 감지**

학생이 답안 안에 자기 이름을 쓰는 경우를 대비한다. 논술형 특성상 드물지만 발생할 수 있다.

- 인식 결과 텍스트에서 명렬표의 이름 문자열을 검색
- 발견 시 해당 부분을 `[학생]`으로 치환한 뒤 LLM에 전달
- 이 검사는 OCR 이후, LLM 전송 이전에 수행

**5. 익명 토큰**

외부로 나가는 모든 요청에서 학생은 `S-{랜덤 8자}` 형태의 토큰으로만 지칭된다. 토큰 ↔ 학생 매핑은 로컬 DB에만 존재하며, 배치마다 새로 생성한다(배치 간 추적 방지).

**6. 피드백 생성 시**

LLM에는 익명 토큰과 점수·루브릭만 전달하고, 피드백문은 "학생"을 주어로 생성한다. **실명은 최종 렌더링 단계에서 로컬 템플릿 엔진이 삽입**한다.

**7. 감사 로그**

전송 게이트웨이는 모든 외부 호출에 대해 다음을 기록한다: 시각, 대상 제공자, 요청 종류, 익명 토큰, 전송 바이트 수, PII 검사 결과. 실제 페이로드는 저장하지 않는다.

**8. 제공자 설정 — 무료 등급 사용 금지 (중요)**

> **이 항목은 "비식별화 후 클라우드" 방침과 직접 충돌할 수 있는 지점이다.**

Gemini API를 포함해 다수의 LLM 제공자는 **무료 등급에서 제출된 내용을 모델 개선에 활용**하고, 유료 등급에서는 활용하지 않는 정책을 둔다. 교사가 개인 API 키를 발급받아 쓰는 구조에서는 무료 키를 쓰기가 쉬운데, 그러면 **학생 손글씨 답안 이미지가 제공자의 학습 데이터로 들어갈 수 있다.**

이는 채점 정확도와 무관한 문제이며, 비식별화로도 해소되지 않는다. 따라서 다음을 강제한다.

- 설정 화면에 **요금제 확인 절차**를 둔다. 학생 답안을 처리하기 전에 교사가 "유료 등급 키를 사용 중이며 제출 내용이 모델 학습에 사용되지 않음을 확인했다"에 명시적으로 동의해야 한다.
- 동의 전에는 **채점 배치 실행을 차단**한다. 루브릭 컴파일(개인정보 없음)은 허용한다.
- 설정 화면에 제공자의 데이터 사용 정책 문서 링크를 노출하고, 정책은 바뀔 수 있으므로 **앱이 판정하지 않고 교사가 확인**하게 한다.
- 동의 시각과 내용을 감사 로그에 남긴다.

이 구분은 §7.7 전체에서 유일하게 기술로 해결할 수 없는 부분이다. 앱이 할 수 있는 최선은 교사가 모르고 지나치지 않게 막는 것이다.

#### 남는 한계 (명시적으로 인정)

**필적 자체는 외부로 나간다.** 답안 본문을 인식하려면 손글씨 이미지를 보내야 하므로 이는 제거할 수 없다. 필적을 개인정보로 보는 해석이 있을 수 있으며, 이 경우 완전 비식별화는 성립하지 않는다.

다만 익명 토큰만 붙은 답안 이미지로 특정 개인을 식별하려면 별도의 대조 자료가 필요하므로, 실무상 가명정보 수준으로 취급 가능하다. **최종 판단은 기관의 개인정보 영향평가에 따른다.** 이 설계는 기술적으로 가능한 최선을 구현할 뿐, 법적 적합성을 보증하지 않는다.

## 8. 교사 검토 UI

검토 화면은 **학생 단위가 아니라 문항 단위**로 묶는다. 같은 문항을 연속으로 보면 판단 기준이 일관되고 속도가 훨씬 빠르다.

```
┌──────────────────────────────────────────────────┐
│ 7번 · 비율을 백분율로 나타내기 (3점)   [12/28 검토] │
├────────────────────────┬─────────────────────────┤
│ 학생 답안 크롭          │ 채점기준                 │
│ (해당 영역만 확대)      │  3점 ○ 두 물건의 …       │
│                        │  2점 ● 정확하게 나타냈으나│
│ 인식 결과:             │  1점 ○ 한 물건만 …       │
│  "180/720×100=25"      │  0점 ○ 나타내지 못하고 …  │
│                        │                         │
│                        │ 예시답안 [보기]          │
│ AI 제안: 2점 (신뢰 0.78)│                         │
│ 근거: "…"              │ [확정] [수정] [건너뛰기]  │
└────────────────────────┴─────────────────────────┘
```

필수 기능:

- 원본 전체 페이지 보기 토글 (크롭이 잘렸을 때)
- 이전/다음 학생 이동, 키보드 단축키 (점수 숫자키 + Enter)
- 일괄 확정 (신뢰도 높은 항목 묶어서)
- 수정 이력 기록 (누가 언제 무엇을 바꿨는지)

**수정 이력은 AI 정확도 측정의 원천 데이터**다. 교사가 AI 제안을 얼마나 바꿨는지 집계하면 문항 유형별 실측 정확도가 나오고, 자동 확정 임계값을 근거 있게 조정할 수 있다.

## 9. 피드백 생성

교사가 점수를 확정한 후 실행한다.

**구성**

1. **문항별 피드백** — 획득 점수 + 적용된 루브릭 조항 + 오답인 경우 예시답안 대비 무엇이 부족했는지
2. **성취수준 판정** — 총점을 `level_cutoffs`에 대입하여 1/2/3수준 결정, 해당 수준 서술문 제시
3. **총평 및 다음 단계** — 성취기준 기준으로 강점과 보완점

**성취수준 컷오프는 채점기준표에 없다.** 예시 파일에도 20점 만점의 수준 구분 기준이 없다. 교사가 평가 저작 단계에서 직접 설정해야 하며, UI에 명시적으로 노출해야 한다.

**피드백 톤**은 대상 학년에 맞춘다. 초등 6학년에게는 짧은 문장, 쉬운 어휘, 지적보다 다음 행동 제시 중심으로 작성한다. 이 지침을 프롬프트에 고정한다.

## 11. 기술 스택 제안

| 영역 | 선택 | 이유 |
|---|---|---|
| 실행 형태 | **교사 PC에서 로컬 실행** — FastAPI가 API와 정적 프런트엔드를 함께 서빙, 브라우저로 `localhost` 접속 | 단일 프로세스, 설치·백업이 단순 |
| 프런트엔드 | **Vite + React + TypeScript (SPA)** | 개인 도구에 Next.js는 과함. 캔버스 조작에는 SPA로 충분 |
| 백엔드 | Python 3.12 + FastAPI | 이미지 처리·OCR 생태계 |
| 이미지 처리 | OpenCV, PyMuPDF | 정합, 차분, PDF 분할 |
| DB | **SQLite** | 단일 사용자. 파일 1개라 백업·이전이 쉬움 |
| 파일 저장 | 로컬 디렉터리 (`~/essay-grader-data/`) | 원본 스캔이 PC를 벗어나지 않음 |
| 작업 큐 | **DB 기반 작업 테이블 + 백그라운드 스레드** | Celery·Redis 불필요. 진행률 폴링으로 충분 |
| 인증 | **없음 (localhost 바인딩)** | 단일 사용자 개인 도구 |
| API 키 저장 | OS 키체인 (`keyring`), 미지원 시 로컬 암호화 파일 | 교사가 설정 화면에서 입력 |
| OCR (답안 본문) | 클라우드 어댑터 — 한국어 손글씨 강한 상용 엔진 | 정확도 우선, 비식별화 후 전송 |
| OCR (PII 영역) | **로컬 엔진** (예: PaddleOCR/Tesseract 한국어) | 이름·번호는 경계를 넘지 않음 (§7.7) |
| LLM | **Google Gemini** (`google-genai` SDK) — 교사가 개인 API 키 입력 | 무료 등급 존재, 멀티모달, JSON 스키마 강제 출력 지원 |
| 모델 선택 | 하드코딩하지 않고 **API로 목록 조회 후 교사가 선택** | 모델 이름은 자주 바뀐다. 고정하면 앱이 먼저 낡는다 |
| 전송 게이트웨이 | 자체 구현 모듈 | 모든 외부 호출의 단일 통로, PII 검사 강제 |

**어댑터와 전송 실행 손잡이**

```python
class OCRProvider(Protocol):
    def recognize(self, image: bytes, hint: RecognitionHint) -> OCRResult: ...

class RawLLMAdapter(Protocol):
    def complete(self, request: LLMOutboundRequest) -> LLMResponse: ...
    def list_models(self, request: OutboundRequest) -> list[str]: ...

provider = LLMProvider(
    gateway=transmission_gateway,
    complete_adapter=raw_adapter.complete,
    list_models_adapter=raw_adapter.list_models,
)
```

`LLMProvider`는 공급자별 상속 기반이 아니라 정확한 하나의 구체 자료형이다.
`TransmissionGateway`와 원시 어댑터 콜백을 합성해 `complete`와 `list_models`의
공개 전송 흐름을 소유한다. 제미나이는 `create_gemini_provider` 생성 함수로 이
손잡이를 만들며, 다른 공급자로 바꿀 때도 원시 어댑터만 갈아 끼운다. 제품
진입점은 정확한 `LLMProvider`만 받고 하위 자료형과 흉내 객체를 거절한다.

## 12. 단계별 구현 계획

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| **P1** | 평가 저작 + 루브릭 컴파일 | 예시 채점기준표 PDF를 넣으면 8개 문항 루브릭 JSON이 나오고 교사가 수정·확정할 수 있다 |
| **P2** | 답안지 템플릿 + 영역 지정 | 빈 답안지 PDF 위에서 문항별 영역을 지정하고 저장할 수 있다 |
| **P3** | 스캔 분할 + 정합 + 필기 추출 | 여러 학생 스캔 PDF가 학생별로 정확히 갈리고, 의도적으로 한 장을 밀어 넣으면 배치가 중단된다 |
| **P4** | 인식 + 채점 엔진 | 인식 결과를 입력으로 주면 루브릭대로 점수가 나온다 (스캔 없이 유닛 테스트 가능) |
| **P5** | 교사 검토·확정 UI | 문항 단위로 검토하고 확정할 수 있으며 수정 이력이 남는다 |
| **P6** | 피드백 생성 + 내보내기 | 확정 점수 기준 개별 피드백과 성적표가 나온다 |

P1과 P4는 학생 답안 없이 개발·테스트할 수 있으므로 먼저 진행한다.

## 13. 파일럿 측정 (구현 전 필수)

정확도는 필기구·스캔 해상도·학생 필체에 좌우된다. 추정에 기반해 설계를 확정하면 안 된다.

**실제 학생 답안 20~30장**으로 다음을 측정한다.

| 측정 항목 | 목적 |
|---|---|
| 이름란 **로컬** OCR + 명렬표 매칭 정확도 | 배정 검증이 실제로 작동하는지. 로컬 엔진 선정 근거 |
| 폐집합 스냅 정확도 (문항 1·5) | 자동 확정 가능 여부 |
| 수치 인식 정확도 (문항 7·8) | 쉼표/소수점 혼동 실태 |
| 서술 OCR 문자 오류율 | LLM 판정 입력 품질 |
| 템플릿 차분 품질 | 연필 vs 볼펜 차이 |

측정 결과에 따라 자동 확정 임계값과 필기구 지침을 정한다.

## 14. 운영 지침 (앱 외부 요구사항)

설계로 해결할 수 없고 운영으로 확보해야 하는 것들이다.

- **필기구**: 검정 볼펜/사인펜 권장. 연필은 인쇄된 회색 괘선과 명도가 겹쳐 필기 추출이 어렵다.
- **스캔 설정**: 300dpi 이상, 흑백 아닌 그레이스케일 이상 권장.
- **급지**: 겹침 급지 감지 기능이 있는 스캐너 사용. 없으면 분할 검증에 더 의존하게 된다.
- **답안지 제작 (수정 가능으로 확정됨)**: 다음을 반드시 넣는다.
  - 네 모서리 **정합 마커** — homography 산출이 안정되고 왜곡 보정 정확도가 오른다
  - 하단 **쪽 번호 마커** (QR/바코드, 1..N) — 급지 사고를 결정론적으로 감지 (§7.1)
  - 문항별 **응답 영역 박스** — 크롭 경계가 명확해지고, 학생이 칸을 벗어나 쓰는 일이 줄어든다
  - 이름·번호란을 **한 곳에 모아 배치** — PII 영역 분리가 단순해진다 (§7.7)

## 부록 A — 예시 시험 컴파일 결과

첨부 파일(수학 논술형 20점)을 컴파일했을 때 기대되는 문항 분류다. 구현 시 이 결과를 P1의 검증 기준으로 사용한다.

| 문항 | 배점 | 유형 | 정답 후보 / 판정 | 라우팅 |
|---|---|---|---|---|
| 1 | 2 | `closed_short` | `{선대칭, 점대칭}` | 자동 |
| 2 | 2 | `closed_table` | 3칸 집합 분류, 기호 `{㉠…㉦}` | 자동 |
| 3 | 2 | `drawing` | 점대칭 도형 완성 | **교사** |
| 4 | 4 | `drawing` | 선대칭+점대칭 도형 | **교사** |
| 5 | 2 | `closed_short` | `{10,000, 6,000, 4,000}` | 자동 |
| 6 | 2 | `composite` | 기호 `{㉠㉡㉢㉣}` + 문장 수정 | 혼합 |
| 7 | 3 | `composite` | 과정(서술) + `{25, 30}` + `{샤프}` | 혼합 |
| 8 | 3 | `composite` | `{6,400}` + `{옳지 않다}` + 이유(서술) | 혼합 |

자동 확정 가능: 약 8~10점 / 교사 검토: 약 10~12점

### 주의: 원본 자료의 기호 불일치

문제지 2번은 보기를 **㉠~㉦ (7개)**로 표기하지만, 채점기준표의 예시답안은 **①, ④, ⑤ / ②, ⑦ / ③**으로 표기되어 있다. 기호 체계가 다르다.

루브릭 컴파일러는 이런 불일치를 **자동으로 고치려 하지 말고, 교사에게 경고로 표시**해야 한다. 컴파일러가 임의로 매핑하면 정답 자체가 틀어진다.
