# 작업 7 보고

## 결과

전송 게이트웨이를 추가했다. 모든 게이트웨이 요청은 제공자 호출 전 등록된 실명과 금지 식별정보를 검사한다. 위반 요청은 감사 기록을 남긴 뒤 예외를 발생시키며 제공자 호출은 실행되지 않는다.

## 실패 뒤 성공 근거

- 실패: `cd backend && pytest tests/test_gateway.py -v` 실행 시 `app.providers` 모듈이 없어 수집 단계에서 실패했다.
- 성공: 구현 뒤 같은 초점 검사는 여섯 건 모두 통과했다.

## 실행한 검사

- `cd backend && pytest tests/test_gateway.py -v` — 여섯 건 통과. 전송 허용, 실명 차단, 차단 시 제공자 미호출, 성공과 차단 감사 기록, 본문과 키 미기록을 확인했다.
- `cd backend && .venv/bin/python -m pytest tests -v` — 마흔두 건 통과. 경고 여섯 건은 기존 의존 도구의 사용 중단 안내다.
- `git diff --check` — 공백 오류 없음.
- 외부 네트워크 호출 흔적 검색 — 앱 코드에서 게이트웨이 밖의 외부 전송 호출을 찾지 못했다. 내부 상태 조회와 상태 점검 경로만 발견됐다.

## 자체 보안 검토

- 검사 실패 경로가 제공자 함수 호출보다 먼저 실행됨을 테스트로 확인했다.
- 감사 기록은 시각, 제공자, 요청 종류, 익명 토큰, 전송 바이트 수, 검사 결과만 기록한다.
- 감사 기록에 본문이나 키가 들어가지 않는지 허용 키 집합과 비밀 문자열 검사로 확인했다.
- 제공자 호출 기능은 게이트웨이 내부의 전달 함수에만 있고, 이 모듈은 네트워크나 키를 직접 다루지 않는다.

## 걱정거리

이미지 속 식별 영역의 마스킹과 답안 본문의 실명 치환은 요청 생성 단계에서 수행돼야 한다. 이번 게이트웨이는 전달된 텍스트의 실명 검사와 전송 차단을 강제하지만, 이미지 좌표의 교차 여부를 검증할 좌표 정보는 아직 요청 계약에 없다. 이후 답안 이미지 전송 기능에서 반드시 해당 메타데이터와 검증을 추가해야 한다.

## 수정 보고

### 반영한 보안 수정

- 요청 자료형을 동결하고 텍스트 목록은 튜플로, 그림 바이트열은 새 바이트열 튜플로 복사했다. 검사 뒤 제공자에는 바로 그 동결 요청만 전달된다.
- 본문과 금지어를 같은 유니코드 정규형으로 바꾸고 보이지 않는 형식 글자를 제거해 조합형과 영폭 글자 우회를 차단했다. 정규화 뒤 빈 금지어는 모든 요청을 막지 않도록 제외했다.
- 제공자와 요청 종류는 비어 있지 않은 안전한 슬러그로, 익명 토큰은 없거나 `S-` 뒤 여덟 영문 또는 숫자 형식으로 생성 시점에 검증한다. 잘못된 값은 감사 기록과 제공자 호출 전에 거부된다.
- 식별정보 예외는 발견한 이름을 포함하지 않고 발견 건수만 알린다.
- 금지어 제공 실패와 감사 기록 쓰기 실패가 제공자 호출 전에 닫히는지, 제공자 예외 뒤에도 감사 기록에 본문과 키가 남지 않는지 검사했다.

### 실패 뒤 성공 근거

- 실패: 새 회귀 검사 실행에서 기존 구현은 요청 변경, 조합형과 영폭 글자 우회, 잘못된 메타자료 허용, 예외의 실명 노출 때문에 아홉 건이 실패했다.
- 실패: 보이지 않는 글자만으로 된 금지어가 정규화 뒤 빈 문자열이 돼 모든 요청을 막는 경계 검사를 추가했고, 이 검사는 수정 전 실패했다.
- 성공: 수정 뒤 초점 검사 열여덟 건과 전체 백엔드 검사 오십사 건이 모두 통과했다.

### 수정 뒤 실행한 검사

- `cd backend && .venv/bin/python -m pytest tests/test_gateway.py -v` — 열여덟 건 통과.
- `cd backend && .venv/bin/python -m pytest tests -v` — 오십사 건 통과. 경고 여섯 건은 기존 의존 도구의 사용 중단 안내다.
- `git diff --check` — 공백 오류 없음.

### 수정 뒤 자체 보안 검토

- 콜백은 검사 뒤 변경할 수 없는 동일 요청만 받으며, 원래 목록과 가변 바이트열을 바꿔도 전송 값은 달라지지 않는다.
- 감사 기록에 들어가는 값은 생성 시점 검증을 통과한 메타자료와 논리 전송 크기로 한정된다.
- 감사 기록과 금지어 조회의 실패는 허용 전송으로 이어지지 않고 제공자 호출 전에 예외가 난다.
- 제공자 예외는 감사 기록에 본문을 추가하지 않는다.

### 남은 걱정거리

이미지 식별 영역 마스킹과 좌표 교차 검증은 여전히 이후 답안 이미지 요청 계약의 책임이다. 또한 이 게이트웨이는 신뢰된 내부 제공자 콜백의 비밀스러운 별도 전송을 통제할 수 없으므로, 이후 제공자 어댑터는 반드시 이 통로만 사용하도록 구조적으로 제한해야 한다.

## 둘째 수정 보고

### 반영한 보안 수정

- 비교용 유니코드 정제에서 형식 글자 외에 결합 그래핌 결합자와 몽골 변형 선택자, 기본 변형 선택자, 보조 변형 선택자 범위를 제거했다. 결합 문자 범주 전체는 제거하지 않아 한글과 일반 본문을 보존한다.
- 제공자는 요청 값이 아니라 게이트웨이 생성 시 고정한다. 현재 허용 목록은 실제 제공자 `gemini`와 시험 제공자 `test-provider`다.
- 요청 종류는 `rubric_compile`, `grade_open_text`, `recognize_classify`, `recognize_transcribe`, `generate_feedback`로 제한했다.
- 익명 토큰은 없거나 P2 생성 계약과 같은 `S-` 뒤 소문자 열여섯진수 여덟 자리만 허용한다.

### 생성자와 요청 계약 변경

- 이전: `OutboundRequest`가 제공자 값을 받았다.
- 현재: `OutboundRequest(purpose=..., text_parts=..., image_parts=..., anonymous_token=...)`이며 제공자 인자를 받지 않는다.
- 현재 게이트웨이 생성: `TransmissionGateway(audit_log_path=..., pii_terms_provider=..., provider="gemini")`.
- Task 8 이후 `get_gateway` 호출부는 실제 제공자에 `provider="gemini"`를 반드시 넘겨야 한다. 시험용 구성은 `provider="test-provider"`를 넘긴다. 요청 생성부에서 제공자를 넘기면 안 된다.

### 실패 뒤 성공 근거

- 실패: 새 계약 검사 실행에서 기존 구현은 게이트웨이 생성 시 제공자를 받지 않고 요청이 제공자를 받았으므로 스물네 건 중 일곱 건 실패와 열일곱 건 오류가 발생했다. 또한 기본 무시 글자와 민감해 보이는 감사 메타자료를 막지 못했다.
- 성공: 수정 뒤 초점 검사 스물네 건과 전체 백엔드 검사 예순 건이 모두 통과했다.

### 둘째 수정 뒤 실행한 검사

### 둘째 수정 뒤 자체 보안 검토

- U+034F와 기본 및 보조 변형 선택자가 이름 문자열 비교를 우회하지 못함을 회귀 검사로 확인했다.
- 제공자 값은 감사 기록 직전 요청에서 읽지 않고, 검증된 게이트웨이 생성 값에서만 읽는다.
- 허용 목록 밖 제공자, 요청 종류, 익명 토큰은 기록 파일을 만들거나 제공자 호출을 실행하기 전에 거부된다.
- 비교용 정제만 바꾸며 실제 전송 본문은 변경하지 않는다.

### 남은 주의사항

### 넷째 수정 뒤 자체 보안 검토

- 마지막 조합 단계를 제거하면 새 회귀 검사가 즉시 실패하므로, 우회의 원인과 수정 경계를 직접 덮는다.
- 기본 무시 글자 제거 전과 후에 조합하므로 기존 조합형 실명, 기존 분해형 실명, 글자 사이 삽입 우회를 모두 같은 비교 형태로 만든다.
- 정제 함수는 새 문자열을 비교에만 쓴다. 요청은 계속 동결 튜플이고, 제공자 콜백은 검사한 바로 그 원본 요청을 받는다.
- 전체 범위 검사는 실제 게이트웨이 차단 경계를 거치며 0.2초 안에 끝났다. 우회가 있으면 콜백 반환을 수집해 누락 수와 대표 코드 포인트를 보여 준다.

### 남은 주의사항

유니코드 기본 무시 글자 속성은 향후 판에서 바뀔 수 있으므로 의존 도구를 올릴 때 고정 범위도 공식 자료와 비교해야 한다. 이미지 식별 영역 마스킹과 좌표 교차 검증은 이후 이미지 요청 계약에서 계속 강제해야 한다.
