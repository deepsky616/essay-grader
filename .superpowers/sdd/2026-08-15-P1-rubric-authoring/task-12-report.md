# 작업 12 보고서

상태: 완료. 작업 수 한도로 주 에이전트가 구현과 읽기 전용 검토를 함께 수행했다.

## 구현

- 평가별 문서 PDF 업로드와 목록 API
- 세 가지 문서 종류 닫힌 집합과 고정 오류 문구
- 1 MiB 조각 읽기와 25 MiB 전체 크기 제한
- 실제 업로드 디렉터리 확인과 심볼릭 링크 거절
- 배타 생성, 권한 600, 임시 파일 검증 뒤 원자 이동과 디렉터리 동기화
- PyMuPDF 실제 해석, 하나 이상 쪽, 암호화 PDF 거절
- 원래 파일 이름을 표시용 basename으로만 저장하고 무작위 저장 이름 사용
- 쓰기, 해석, 이동, 자료 저장 실패 때 생성 파일 정리와 세션 되돌림
- 목록 응답에서 로컬 저장 경로 제외

## 판정

Ruling: 계획의 전체 메모리 읽기와 `%PDF` 머리말 확인만으로는 깨진 파일, 큰 파일, 부분 저장을 막을 수 없어 조각 읽기와 실제 PDF 해석, 원자 게시를 정본 계약으로 삼았다 — 원문 파일은 로컬에만 남아야 하고 데이터베이스와 파일 저장이 어긋나면 안 되기 때문이다 — 이 판단이 틀리면 단순한 업로드 구현보다 코드가 길고 25 MiB를 넘는 정상 자료를 올릴 수 없다.

Ruling: 암호화 PDF는 뒤 텍스트와 이미지 추출을 안정적으로 수행할 수 없으므로 업로드 단계에서 고정 400으로 거절한다 — 컴파일 단계에서 뒤늦게 실패해 원인을 숨기는 일을 막기 위해서다 — 이 판단이 틀리면 암호를 별도로 받는 흐름이 필요하다.

## 남은 위험

- 업로드 디렉터리 확인과 파일 생성 사이의 로컬 파일시스템 경쟁은 운영체제 수준 격리까지 제공하지 않는다.
- 파일 정리에 실패한 경우 더 강한 삭제 수단으로 다시 시도하지 않는다. 전용 평가 삭제 저장 서비스는 뒤 작업에서 보상 가능한 흐름으로 묶어야 한다.
