## 실패 뒤 성공 근거

- 첫 실행에서 `app.providers.base`, `app.providers.credentials`, `app.api`가 없어 수집 오류가 났다. 시험을 먼저 둔 뒤 모듈을 구현했다.

## 계획 순서와 게이트웨이 계약에 따른 차이

- `main.py`에는 아직 없는 평가와 문서 라우터를 불러오지 않고 설정 라우터만 등록했다.
- `models/__init__.py`는 현재 있는 `Base`, `Assessment`, `AppSetting`만 내보낸다.
- 고정된 예비 모델 이름을 설정에서 제거했다. 모델을 고르기 전에도 목록을 조회할 수 있도록 제공자 모델 인자를 선택값으로 만들었다.
- `list_models`를 게이트웨이 허용 목적에 추가했다. 실제 설정 팩터리는 `provider="gemini"`, 격리 시험은 `provider="test-provider"`를 쓰며 둘 다 감사 기록을 확인한다.
- 제미나이 어댑터는 게이트웨이를 주입받고 모든 완성과 모델 목록 호출을 그 경계 안에서 수행한다. 시험용 제공자 도구 주입점도 외부 호출 격리에만 쓴다.
- 외부 제공자 오류 원문은 API 응답에 넣지 않는다. 원문에 키가 들어 있어도 고정된 오류만 반환한다.
- 자료 정책 확인값과 갱신 시각은 저장하지만 학생 답안 처리 차단은 이 작업에 연결하지 않았다. 해당 연결은 P3 범위다.

## 자체 보안 검토

- API 키는 운영체제 자격 정보 저장소를 우선하며 데이터베이스, 설정 응답, 감사 기록에 넣지 않는다.
- 대체 파일은 생성 시점부터 권한 600을 쓰고, 읽을 때도 일반 파일과 정확한 권한을 확인한다. 기호 연결을 따라가지 않는다.
- 운영체제 저장 성공 시 낡은 대체 파일을 지우며, 지우기 API는 두 저장 위치를 모두 정리한다.
- 모델 목록 감사에는 제공자, 목적, 빈 본문의 크기만 남고 키와 응답 목록은 남지 않는다.
- 제공자 완성 호출은 검사된 불변 본문과 그림만 사용한다.
- 앱 시작과 내보내기 목록에 미래 모듈 참조가 없는 것을 확인했다.

## 걱정거리

- 운영체제 자격 정보 저장소가 없을 때 대체 파일은 권한으로 보호되는 평문이다. 장비 저장 장치 암호화와 사용자 계정 보호가 필요하다.
- 현재 P1에는 학생 명렬 자료가 없어 실제 팩터리의 식별정보 용어 공급자는 빈 집합이다. 학생 자료를 다루는 단계에서 명렬 공급자 연결이 필요하다.
- 전체 검사 경고 7개는 시험 클라이언트, 제미나이 도구, 피디에프 도구의 사용 중단 예정 알림이다.

## 수정 라운드 1

### 상태

검토 지적 일곱 묶음을 반영했다. 평문 대체 저장을 없애고, 자격 정보 삭제 확인, 원자 쓰기, 정책 확인 사건, 모델과 키 조합 검증, 설정 동시 저장을 강화했다.

### 실패 뒤 성공 근거

- 자격 정보 수정 전 검사는 3개 성공, 13개 실패였다. 새 암호화 키 인자 부재, 평문 저장 허용, 삭제 오류 삼킴이 원인이었다. 구현 뒤 16개가 모두 성공했다.
- 설정 API 수정 전 검사는 9개 성공, 10개 실패였다. 정책 시각과 사건 부재, 키 없이 모델 저장 허용, 목록 밖 모델 허용, 키 변경 뒤 모델 잔존, 삭제 오류 미처리, 첫 저장 경쟁의 고유 제약 충돌을 각각 재현했다. 구현 뒤 19개가 모두 성공했다.
- 동시 저장 검사는 예전 읽기 뒤 넣기 흐름에서 `app_settings.key` 고유 제약 오류로 실패했다. SQLite 충돌 시 갱신 한 문장으로 바꾼 뒤 두 작업이 겹쳐도 행 하나만 남았다.

### 구현 내용

- 운영체제 저장소 실패 시에는 `EG_CREDENTIAL_ENCRYPTION_KEY`로 전달된 명시적 펄넷 키가 있을 때만 인증 암호문을 쓴다. 암호화 키를 파일로 만들거나 대체 파일 곁에 저장하지 않는다.
- 암호화 키가 없거나 잘못됐거나 암호문이 변조되면 비밀값 없는 고정 오류로 닫는다. 암호문 바이트에 원문 API 키가 없음을 검사한다.
- 대체 저장은 같은 폴더에 권한 600의 일반 임시 파일을 배타 생성하고, 쓰기와 파일 동기화 뒤 `os.replace`로 교체한다. 가능한 경우 부모 폴더도 동기화한다.
- 기존 파일과 열린 파일의 장치와 파일 번호를 비교한다. 기호 연결, 넓은 권한, 비일반 파일, `O_NOFOLLOW` 미지원은 거부한다. 교체 실패 때 기존 암호문을 보존하고 임시 파일을 지운다.
- 키체인 삭제가 실패하면 실제 값 부재를 다시 확인한다. 삭제와 확인이 모두 실패하거나 값이 남아 있으면 삭제 API는 503으로 닫고 모델 선택도 보존한다.
- 키를 새로 저장하거나 성공적으로 지우면 이전 모델 선택을 지운다. 모델 저장은 현재 키로 게이트웨이를 거쳐 목록을 조회하고 그 목록에 있는 이름만 허용한다. 제공자 오류 원문은 응답에서 숨긴다.
- 자료 정책 확인은 현재 참거짓 값을 계속 유지하면서, 문구 판과 확인값과 마이크로초 단위 확인 시각을 별도 사건 행으로 매번 추가한다. 같은 참 값을 거듭 보내도 새 사건과 새 시각이 생긴다.
- 설정 쓰기는 SQLite 충돌 시 갱신을 사용해 읽기 뒤 넣기 경쟁을 없앴다.
- `cryptography>=46.0`을 직접 의존성으로 선언하고 `uv.lock`에 반영했다.

### 계획과 달라진 점

- 처음 작업 계획의 권한 600 평문 대체 파일보다 설계 11절의 암호화 요구를 우선했다. 평문 대체 파일은 더 이상 읽거나 쓰지 않으며, 예전 평문 파일은 안전 오류로 거부된다.
- 모델 선택 API가 단순 문자열 저장이 아니라 외부 목록 재확인을 수행하므로, 선택 때도 `list_models` 전송 감사 한 건이 생긴다.
- 자료 정책은 `AppSetting` 현재값 외에 `DataPolicyAcknowledgement` 사건 표를 추가했다. P3는 기존 현재 참거짓 키를 그대로 게이트로 쓸 수 있다.

### 자체 보안 재검토

- 대체 파일과 임시 파일 어디에도 API 키 원문이나 암호화 키를 쓰지 않는다.
- 키, 제공자 오류, 암호 해제 오류는 API 응답과 감사 기록에 넣지 않는다. 오류 응답은 고정 문구만 쓴다.
- 검사한 파일과 실제 읽은 파일이 같은지 확인하며 기호 연결을 따라가지 않는다.
- 교체 전에 파일 동기화를 마치며, 교체 실패 경로에서 예전 암호문과 임시 파일 상태를 검사한다.
- 삭제 성공이 확인되기 전에는 대체 파일과 모델 선택을 지우지 않는다. 회복된 키체인에서 이전 키가 다시 나타나는 시험도 삭제 성공으로 잘못 응답하지 않는다.
- 현재 키와 모델 목록을 한 요청 흐름에서 확인한 뒤 목록 안의 모델만 저장한다.
- 정책 현재값 갱신과 사건 추가는 같은 데이터베이스 거래에서 끝난다.

### 걱정거리

- 운영체제 저장소를 쓸 수 없는 환경에서는 운영자가 별도로 만든 펄넷 키를 환경 설정으로 제공하고 안전하게 백업해야 한다. 이 키를 잃으면 기존 암호문을 복구할 수 없다.
- 예전 판이 만든 권한 600 평문 파일은 자동 옮김 없이 거부된다. 운영체제 저장소가 회복되거나 평문 파일을 안전하게 없앤 뒤 키를 다시 입력해야 한다.
- 키체인 삭제와 조회가 모두 막힌 동안에는 안전을 위해 삭제 API도 막힌다.
- 전체 검사 경고 7개는 기존 외부 도구의 사용 중단 예정 알림이다.

## 수정 라운드 2

### 상태

정책 확인 원문 보존과 키 및 모델 결합의 단일 프로세스 직렬화를 구현했다.

### 실패 뒤 성공 근거

- 첫 설정 API 실행은 17개 성공, 6개 실패였다. 정책 원문 칸과 상수 부재, 모델 지문 부재, 지문 불일치 모델 노출, 키 저장과 삭제 부분 실패 뒤 모델 잔존, 모델 목록 조회 중 키 저장 진입을 각각 재현했다.
- 전역 잠금과 지문 결합 구현 뒤 설정 API 23개가 성공했다.
- 뒤 처리 단계의 안전한 현재값 읽기 함수가 없다는 검사는 속성 오류로 실패했다. 지문 검증을 포함한 `read_valid_llm_model`을 추가한 뒤 해당 검사와 설정 API 24개가 모두 성공했다.
- 실제 동시 요청 검사에서 잠금 전에는 이전 키의 모델 목록 조회가 멈춰 있는 동안 새 키 저장이 시작됐다. 잠금 뒤에는 목록 조회를 풀기 전까지 새 키 저장소 진입 사건이 생기지 않았고, 두 요청 종료 뒤 모델과 지문이 모두 무효화됐다.

### 정책 확인 사건

- 설계 7.7절 문구를 `DATA_POLICY_WORDING_TEXT` 상수로 고정했다.
- 고정 문구는 `유료 등급 키를 사용 중이며 제출 내용이 모델 학습에 사용되지 않음을 확인했다`이다.
- 매 사건에 `wording_text`, `wording_version`, `acknowledged`, `confirmed_at`을 모두 저장한다.
- 같은 참 값을 거듭 확인한 검사에서 두 사건의 문구가 상수와 정확히 같고, 판은 `paid-tier-no-training-v1`로 같으며, 확인 시각은 서로 다름을 확인했다.

### 잠금과 지문 계약

- 모듈 전역 `RLock` 하나를 설정 API의 가장 바깥 잠금으로 쓴다. 설정 조회, 키 저장과 삭제, 모델 목록 조회, 모델 확인과 저장, 정책 사건 저장이 같은 잠금을 따른다.
- 단일 프로세스 안에서는 키 저장과 삭제가 모델 목록 확인 또는 모델 저장과 동시에 실행되지 않는다. 잠금은 제공자 목록 호출이 끝날 때까지 유지한다.
- 키 저장과 삭제 시도는 잠금 안에서 모델과 지문을 먼저 한 삭제 문장으로 지우고 커밋한다. 그 뒤 자격 정보 저장소를 바꾸므로 외부 저장이 부분 성공하거나 결과가 불확실해도 예전 결합은 남지 않는다.
- 모델 저장은 잠금 안에서 현재 키를 읽고 목록을 확인한 뒤 키를 다시 읽는다. 앞뒤 지문이 같을 때만 모델과 지문을 커밋 한 번으로 같은 데이터베이스 거래에 저장한다.
- 지문은 영역 구분 바이트를 붙인 키에 샤 이백오십육을 적용한 64자리 값이다. 키 원문은 데이터베이스에 저장하지 않는다.
- 설정 조회와 공개 `read_valid_llm_model` 함수는 현재 키 지문과 저장된 지문을 일정 시간 비교하고, 다르거나 하나라도 없으면 모델을 돌려주지 않는다. P3는 원시 설정 행 대신 이 함수를 쓸 수 있다.

### 부분 실패 회귀 검사

- 키체인에는 새 키가 저장됐지만 낡은 대체 경로 정리가 실패하는 경로에서 API는 503을 반환하고 이전 모델과 지문은 모두 사라진다.
- 키체인 삭제와 확인이 모두 실패하는 경로에서도 모델과 지문은 먼저 사라지고, 키체인이 회복되면 이전 키는 남아 있으나 유효 모델은 없다.
- 이전 키의 목록 조회가 멈춘 동안 새 키 요청을 동시에 보낸 경로에서 새 키 저장은 잠금 뒤에 대기한다. 이전 모델 저장이 끝나더라도 이어진 키 변경이 결합을 다시 지운다.

### 자체 보안 재검토

- 잠금은 항상 설정 동작의 가장 바깥에서 잡는다. 잠금 안의 키 변경 경로는 데이터베이스 무효화 뒤 외부 저장소를 호출하고, 모델 경로는 외부 목록과 키 재확인 뒤 데이터베이스 결합을 커밋한다.
- 모델과 지문 쓰기 사이에는 커밋이 없으며 둘째 쓰기가 실패하면 요청 세션 종료 때 전체 거래가 되돌아간다.
- 키 변경 경로는 외부 저장소 호출 전에 무효화 거래를 커밋하므로, 외부 저장 성공 여부와 상관없이 예전 결합이 되살아나지 않는다.
- 지문만으로 원문 키를 되찾을 수 없고, 기존 API 키 비노출 검사도 모든 설정 행을 다시 확인한다.
- 제공자 오류 원문은 고정 오류 응답으로 바뀌며, 모델 목록 감사에는 키나 목록 내용이 들어가지 않는다.
- 정책 사건은 현재값 갱신과 같은 거래에서 원문, 판, 값, 시각을 저장한다.

### 걱정거리

- 이 잠금은 설계대로 단일 프로세스에서만 효력이 있다. 여러 작업 프로세스로 실행하면 프로세스 사이 직렬화가 없으므로 한 작업 프로세스 구성을 유지해야 한다.
- 모델 목록 외부 호출 동안 설정 잠금을 유지하므로 제공자가 느리면 다른 설정 요청도 기다린다. 키와 모델 결합을 보장하기 위한 의도된 선택이다.
- 중간 개발판 데이터베이스에 이미 정책 사건 표가 있다면 새 `wording_text` 칸을 자동으로 더하는 이행 도구는 아직 없다. 현재 개발 검사와 새 데이터베이스는 최신 표를 만든다.
- 전체 검사 경고 7개는 기존 외부 도구의 사용 중단 예정 알림이다.
